# 循证保研 Product Memo

## 1. 目标用户与核心痛点

目标用户是准备计算机类保研夏令营或预推免的本科生，尤其是需要同时准备多个学校、院系和导师的学生。目前没有可核实的正式用户访谈记录，因此以下内容是基于真实申请流程、产品使用反馈和公开资料形态形成的待验证假设，而不是伪装成调研结论。

这个群体的难点并不是“缺一个能问问题的聊天框”，而是资料和训练之间断裂：招生通知、往年机试、学长面经、导师主页和自己的简历散落在不同平台；相似学校的考核方式又不能直接混用。通用大模型可以快速出题，却很难稳定回答“为什么这所学校更可能问这道题”，还可能把旧年份、其他院系或无来源内容写成事实。学生最终得到的是一份看似完整、但无法判断可信度的题单。

## 2. 产品设计与关键取舍

“循证保研”把准备过程收敛为一个项目化闭环。每所学校是一个独立备考项目，项目下保存申请目标、联网资料和用户上传资料。系统先用 Tavily 搜索公开来源，再通过正文提取、URL/内容指纹去重、规则预筛和 DeepSeek 结构化复核，判断资料是否匹配学校、院系、年份和考核场景。筛选后的资料才进入三个训练关卡：机试、面试题单、项目追问。题目版本只读保存，证据默认收起，需要时可查看来源、摘录和原链接。

产品相对直接使用 ChatGPT 的差异是：它记得“为哪所学校准备”，能复用同一项目的资料，并明确区分官方材料、回忆题、证据推断、通用补充和 AI 生成。第三关还把唯一当前简历与导师/课题组公开方向结合，只提出可能追问，不伪造标准答案。

刻意没做的内容包括面试官端、岗位/JD、录取概率、服务器代码判题、题单自由编辑、标准答案、学习进度、多用户和云同步。它们会扩散首版范围，或在证据不足时制造不可靠的确定性。代码编辑器只用于草稿与一次性 AI 复盘，不宣称真实判题结果。

## 3. 版本迭代

最初方案更接近通用 AI 面试聊天页，功能多但用户不知道从哪里开始。第一轮改版删除面试官模式和岗位字段，将产品聚焦为求职者视角的保研工具。第二轮把主界面改成 ChatGPT 式项目侧栏和三个独立页面，移除底部聊天框与重复入口，并建立“学校项目—精细申请目标—资料—题单版本”的隔离关系。

真实联网后暴露出更关键的问题：题单大量显示“AI 补充”，说明搜索结果虽多，但没有真正成为可用证据。系统因此从普通字符串规则升级为两阶段筛选：规则负责去重、时效和明显无关项，DeepSeek 再按目标匹配度、证据等级和适用关卡审查。随后发现 DeepSeek Responses 返回同时包含推理文本和最终结构化输出，旧解析误把推理文本当 JSON；修复后只读取 `output_text` 并使用严格 JSON Schema。最后补齐项目三点菜单、置顶和可靠删除，让项目切换与管理更接近用户熟悉的 ChatGPT 交互。

## 4. 如果再给一周

第一优先级是访谈 5–8 名近期参加过计算机保研考核的学生，观察他们如何找资料、判断可信度和复盘失败；第二是用 3–5 个真实院校目标建立带人工标注的来源集，量化检索召回率、有效证据率和题目可追溯率；第三是为常见院校站点增加定向解析器，并补齐当前工作台的端到端自动化测试。完成这些验证后再做公网部署、任务队列与安全代码执行，而不是继续堆新按钮。

## 5. AI 工具与开源使用

OpenAI Codex 用于需求拆解、代码实现、调试、测试和界面迭代；DeepSeek 用于资料二次筛选、结构化生成和一次性代码复盘；Tavily 用于公开网页候选搜索。界面组织参考了开源项目 `zmy15/interview-agent` 的求职者工作台思路，但删除了面试官、岗位和认证等模块，并重新实现为保研项目、资料证据和三关题单。UI 基础组件来自 shadcn/ui、Base UI 与 Lucide，具体许可和改动范围已写入仓库 `THIRD_PARTY_NOTICES.md`。所有密钥、数据库和用户资料均排除在 Git 仓库之外。
