# 循证保研 Product Memo

## 用户与问题

用户给定的目标人群是准备计算机相关保研考核的本科生。需求中最关键的判断不是“再做一个 AI 面试聊天框”，而是把调查和训练串成闭环：学生往往不知道今年、这个院系、这个项目、这个批次究竟考什么；网络经验又容易跨年份、跨批次、跨项目混用。直接生成题单会把不确定性藏起来，也难以解释为什么练这道题。

**没有进行真实用户访谈。** 当前痛点来自挑战说明和用户提供的完整实施规格，仍属于待验证假设，不写成用户研究结论。

## 产品取舍

核心功能是“可追溯训练”：目标 → 来源 → 证据 → 结论/缺口 → 三关题目 → 实际回答 → 反馈 → 复测。首屏不是营销页，而是调查档案核对工作台；右侧证据抽屉让用户在不离开上下文的情况下查看精确摘录、年份、范围和访问状态。

刻意不做：服务器执行用户代码、录音视频、多智能体、向量数据库、录取概率和导师评分。前两项需要明显更高的安全与基础设施成本；后三项会在证据不足时制造“看起来很智能”的假确定性。机试保留自报 OJ 结果和 AI 审查，但两者永不显示为真实沙箱判题。

## 从想法到本版本

最初范围非常大，包含完整资料调查、三关训练、外部服务和部署。实现时先交付一个最窄的纵向闭环：三份虚构来源形成三条不同可信度的结论；结论各自打开原文；其中一条经验线索生成原创机试变式；用户作答后产生明确标记的演示反馈并保存。随后才补 URL/PDF 导入、会话隔离、安全校验、三关详细交互和部署文件。

主要技术问题是保持“演示可用”与“真实模式不造假”同时成立。解决方式是让演示来源拥有内部可定位页面，并让所有模拟结果携带 `simulated` / “未调用模型”标识；真实模式缺密钥直接报错。另一个问题是无服务器与 SQLite/上传的冲突，因此选择单实例 Node + 持久化卷。

## 待验证假设

- 用户是否愿意先花 10–20 分钟核对档案，再进入训练。
- 证据抽屉的信息密度是否合适，还是需要按“快速看/审计看”分层。
- 项目追问中，用户确认简历事实的成本是否过高。
- 哪些官方站点的正文抽取最常失败，是否值得增加站点级解析器。
- 三轮复测是否足够观察理解稳定性。

## 如果再给一周

先访谈 5–8 名近期参与过夏令营/预推免的学生，观察他们实际整理资料和复盘面试的过程；基于失败样本改进站点抽取和 PDF 定位；接入一个受限安全判题器；为研究任务增加可恢复队列与中断标记；再用真实但已授权、可公开引用的目标完成一次端到端评测。

## AI 工具使用

Codex 用于规格拆解、Next.js/SQLite 实现、测试编写、界面迭代和安全检查；网页检索用于核对 Next.js、Drizzle 与 Tavily 的当前官方文档；Playwright 用于桌面/移动核心流程。没有伪造访谈、用户反馈、远端仓库或部署结果。
